# 真实对照实验：无提示条件下，AI 会不会漏掉顺序敏感的组合场景断言？

## 结论先说

**6 次独立、无提示的盲测生成，6 次都在组合场景（GOLD 会员门槛 + VIP100 优惠券同时满足）里，于同一个测试函数内同时断言了 `membershipDiscount`、`couponDiscount`、`discount` 三个字段的正确拆分值。0/6 遗漏。**

这是如实报告，不是筛选过的结果——方法论、原始数据、失败该长什么样都写在下面，包括为什么这个结果本身值得怀疑地多读几遍。

## 方法

1. **干净的输入文档**：`spec/requirement.md`、`spec/acceptance.md`、`spec/openapi.yaml`，业务场景与原 `business/` 目录相同（GOLD 会员/VIP100 优惠券/订单优惠预览接口），但文字重写为不含任何测试暗示——没有"这条规则容易漏""不能只验证最终金额"这类元评论，没有单独标出"这是关键规则"，验收表 7 行用完全相同的格式呈现，组合场景那一行不做任何视觉或措辞上的特殊处理。对照见 `tests/generated/PROVENANCE.md` 里列出的、原始 `business/acceptance.md` 和 `tasks/task-package.md` 里存在但这次被剔除的具体提示内容。
2. **黑盒隔离**：真实（正确）实现通过 `uvicorn app.main:app --port 8811` 常驻运行，被测代码从未出现在任何一次盲测 agent 的工作目录里。每次的 prompt 明确指示"不要读 app/、business/、tests/ 等目录下的任何文件，把接口当黑盒测"。**这是指令约束 + 物理隔离（agent 自己的目录里只有文档，没有源码文件），不是文件系统硬沙箱**——如果某次 agent 存心不听话去别处翻文件，没有技术手段能百分之百拦住。用来交叉核实是否偷看的办法见下面"完整性核查"。
3. **6 次完全独立的会话**：每次都是全新的 general-purpose agent，互相之间没有共享上下文；6 次收到的 prompt 逐字节相同，只有输出路径不同（差异见 `trial-1/prompt.md` 与 `trial-2/prompt.md` 的 diff，只差一行路径）——没有因为某次结果不理想就调整过提示词。
4. **独立执行，不采信自报**：每次生成完，我们用 `experiments/real-generation/run_trial.py` 重新对真实服务跑一遍 pytest，取这次独立执行的结果，不采信 agent 自己在回复里报的"是否通过"。
5. **人工判定为准，脚本只做初筛**：`scan_trial.py` 是字符串层面的启发式扫描，负责标出候选函数；真正的判定写在每个 `trial-N/review-notes.md` 里，是逐行读代码后的结论。

## 完整性核查：有没有偷看实现？

没有发现任何一份测试文件里出现只有读过 `app/service.py` 才可能知道的信息（比如 `decisionTrace` 里的具体步骤字符串 `CHECK_GOLD_LEVEL`/`APPLY_GOLD_DISCOUNT`——六份都只对 `decisionTrace` 做了"是字符串列表"的类型检查，没有一份断言过具体内容）。trial-5 断言了 `discountSources` 的具体取值（`"GOLD_MEMBERSHIP"`、`"VIP_COUPON"`），但这两个字符串通过合法途径（提示词允许的黑盒探测：真的往 `http://127.0.0.1:8811` 发请求看响应）就能拿到，不需要读源码——反而是"确实做了黑盒探测"的正面证据，细节见 `trial-5/review-notes.md`。

## 这个结果本身要怎么读——诚实的方法论限制

6/6 全对，比预想的更整齐，值得多想一层，而不是直接当"AI不会犯这个错"的证明：

1. **验收表本身把期望值摆出来了**。每一行都直接写了 `membershipDiscount=100；couponDiscount=100；discount=200；finalAmount=1000` 这种具体数字，任务说明也明确要求"每条用例都需要有对应的自动化测试提供证据"。对一个还算称职的模型来说，把表格第5行的四个数字原样转成四个 assert，是相当机械的转录动作，未必需要它"独立意识到这是个容易漏的组合场景"。换句话说，这次实验测的更准确地说是**"给定明确期望值表格时，会不会遗漏转录"**，而不是**"在没有明确期望值、只有模糊业务描述时，会不会独立想到要测这个组合"**——后者是更难、也更接近"AI 生成测试到底可靠到什么程度"这个问题本源的测法，这次没有测。
2. 但这恰恰也是这次实验最有价值的地方：**原始 `business/acceptance.md` 里 AC-004 那一行同样直接给出了具体数字（甚至连 trace 字符串都给了），按这次的观察，一个正常水平的模型拿着这么清楚的表格几乎不会漏填——这跟"AI生成测试遗漏了AC-004"这个原始演示材料所呈现的结果是矛盾的。** 这进一步印证了 `tests/generated/PROVENANCE.md` 里从文件时间戳/无生成日志推出的结论：原始的"generated"测试套件更像是照着"要制造出这样一个失败"反向构造出来的，不是这次观察到的、一个模型在类似清晰程度的验收表下会自然产生的结果。
3. **样本量小（6次）**，且都在同一次会话窗口、同一底层模型状态下发起，不构成跨模型版本、跨时间的统计意义上的"概率"。
4. 隔离手段是指令约束而非硬沙箱（见"方法"第2点），信任程度有限，虽然本次逐份检查没有发现违规痕迹。

## 如果想设计一个更难、更接近"自然遗漏"的后续实验

把验收文档从"给具体数字的表格"换成纯业务描述（不给 `membershipDiscount=100` 这种精确数字，只说"当两者都满足时应该都生效"），强迫模型自己去黑盒接口探测、自己推导期望值、自己决定测哪些场景——这样更接近"AI 独立设计测试用例"而不是"AI 转录一张已经写好答案的表格"。这个设计没有在本轮做，留在这里供下一轮参考。

## 可重跑

```bash
# 1. 起真实服务（黑盒被测对象）
source .venv/bin/activate
uvicorn app.main:app --host 127.0.0.1 --port 8811 &

# 2. 重新执行任意一次已生成的测试（不重新生成，只重新跑）
python experiments/real-generation/run_trial.py trial-1   # 换成 trial-2 ... trial-6

# 3. 启发式扫描辅助复核
python experiments/real-generation/scan_trial.py trial-1
```

若要重新做一轮全新的盲测生成（而不是重跑已有产物），需要重新按 `trial-N/prompt.md` 里的完整提示词、逐字节不改地发给全新会话的 agent——本轮的 6 份 prompt.md 彼此除输出路径外完全相同，可直接复用同一份提示词模板。
