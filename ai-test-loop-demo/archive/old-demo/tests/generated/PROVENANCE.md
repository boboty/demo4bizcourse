# 定位说明：这套测试是什么，不是什么

`tests/generated/test_orders.py` 是**为教学演示构造的失败模式装置**，不是某一次真实 AI 生成事件的记录。使用这份材料讲课或写文章时请遵守这个边界，避免误用为"实证"。

## 依据（可核实，非推测）

- 本目录在纳入版本库之前没有 git 历史；`business/`、`app/`、`tests/generated/`、`tests/verified/`、`scripts/`、`README.md` 等全部文件的文件系统创建时间都落在 **2026-08-11 12:08:15–12:15:06 这 7 分钟内**，看不出"先有一次独立的 AI 生成事件、隔了一段时间、再有一次独立的修复/验收事件"这种时间上分离的历史，更像一次连续搭建。
- 目录里没有任何对话日志、模型调用记录、生成时间戳，或其他可追溯到具体一次生成行为的痕迹。
- `tasks/task-package.md` 的"验收标准"一节写明："AC-004 与 AC-005 要验证 `membershipDiscount` 和 `decisionTrace`，不接受只验证 HTTP 200 或最终金额"——这相当于把答案预先写进了任务说明；`business/acceptance.md` 的 AC-004 一行直接给出了 `CHECK_GOLD_LEVEL`、`APPLY_GOLD_DISCOUNT` 这些具体 trace 字符串。一次真实的、无提示的生成不会预先拿到这些提示。

## 这份材料能用来说明什么

- 可以用来演示"结果正确不等于判断过程被验证"这个道理本身，以及"独立验收"这套机制具体怎么运作、怎么判定、判定依据是什么。
- **不能**被引用为"AI 真的会犯这种错"的统计实证，不能用来支撑"AI 生成测试遗漏关键规则的概率是多少"这类结论——这套素材从一开始就是照着失败模式反向构造出来的，不是观察到的样本。

## 真实的、无提示的对照实验在哪，结果是什么

`experiments/real-generation/` 是一次真正独立多次、无引导提示的生成实验：每次开一个全新会话，只给一份剥离了任何暗示的需求文档和验收用例，观察生成结果是否遗漏组合场景下的会员优惠与优惠券优惠拆分断言。方法、每次运行的完整 prompt、原始输出、独立执行结果和如实汇总见该目录下的 `SUMMARY.md`。**这才是可以用来支持或反驳"AI 会不会犯这种错"这类结论的材料。**

**如实报告结果：6 次独立盲测，6 次都正确断言了组合场景下的拆分（0/6 遗漏）**——这个结果本身跟本目录 `test_orders.py` 所演示的失败模式是矛盾的，进一步支持了上面"这是构造出来的装置"这个判断。`SUMMARY.md` 里也写清楚了这次实验的方法论局限（验收表直接给了期望数字，测的更接近"会不会漏转录"而非"会不会独立想到测这个场景"），不要脱离限制条件引用这个 6/6。
