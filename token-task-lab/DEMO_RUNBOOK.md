# DEMO_RUNBOOK

## 课堂位置

### Demo 1｜第二讲“四问”之后

不要重新开场，直接接：

> 刚才说条件拿不到就应该停，我们直接看它会停在哪里。

1. 打开天津货代场景。
2. 输入客户原话。
3. 观察任务理解、已知条件、缺失条件、下一步动作。
4. 重点看哪一步需要外部事实，哪一步需要人工确认。
5. 不打开 Token 面板。

目标：验证“四问”是任务设计条件，不是抽象框架。

### Demo 2｜第三讲调用链之后

直接说：

> 刚才从正面看是一件事，现在把同一次运行翻过来看背面。

1. 使用 Demo 1 的同一 `run_id`。
2. 打开运行背面。
3. 先看调用步骤，再看 usage。
4. 强调：任务数 ≠ 调用次数 ≠ Token 数。
5. 运行/回放 A、B、C；时间允许再看 D。

#### A 档两种现场结果都成立

- 若模型编造船期/价格：只问来源、舱位、价格依据，不重新讲“验证为什么重要”。
- 若模型谨慎停下：指出它自己暴露了缺失条件，直接推进 B。

#### D 档

必须是真实执行出来的低效版本，不能改数字。

## 课前准备

课堂默认回放已验证记录。上课前跑一次：

```bash
export LLM_BASE_URL=... LLM_API_KEY=... LLM_MODEL=...
python scripts/record_runs.py        # 真实执行 A/B/C/D，写入 runs/
```

脚本会打印各档的模型调用 / 工具调用 / 输入输出 Token 对比表——这张表就是讲 D 档时的底稿。
provider 未配置时脚本直接退出，不会生成占位数字。

仓库内另存有一份 C 档结构示例记录（`evidence_level=structure_only`，Token 字段为 null），
用于确认回放链路本身可用；它不是「已验证记录」，别拿它当真实用量讲。

## 课堂故障策略

- 预先保存一份完整、已验证运行记录（见上）。
- 网络/provider 异常时直接回放，不现场排障。
- 真机和回放结果不完全一致是允许的；课堂讲的是结构，不是追求固定答案。
- 完全没有 provider 时页面仍可打开：回放记录照常，现场运行只会得到结构示例。

## 讲师检查清单

课前确认：

- [ ] Demo 1 默认不显示 Token（页面收起运行背面时，HTML 里也不含 Token 数字）
- [ ] Demo 1 与 Demo 2 能用同一 run_id 串起来
- [ ] A/B/C/D 模式标签清楚
- [ ] Token 数字来自真实运行日志（页首环境提示里的「真实运行 N 份」N ≥ 1）
- [ ] 未验证船期/运价没有被标成真实事实
- [ ] 至少一份完整回放记录可离线打开
- [ ] D 模式确实比合理版本存在可解释的低效消耗（拿 `record_runs.py` 的对比表说话）
