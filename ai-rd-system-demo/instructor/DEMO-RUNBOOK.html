Demo 2｜同一个任务，改用五要素重新交办

服务判断：从“让 AI 写代码”，到“让 AI 推进一个可验收任务”。

讲师演示 · 15 min

./scripts/reset_base.sh

新 Codex 会话，粘贴五要素任务包：

# 任务 A｜五要素可交办任务 ## 一句话需求 融资申请列表增加客户名称、融资状态筛选，并支持导出。 ## 01 背景｜为什么做 - 业务方每天手工导出、肉眼筛选，对账耗时且容易出错。 - 本期目标是把这段人工去掉，不改现有业务流程。 - 已定：不新增页面，在现有列表上扩展。 ## 02 边界｜哪些能改，哪些绝对不能碰 - 可改：融资申请列表的查询、筛选与导出。 - 不可改：申请创建、审批流转、状态机逻辑。 - 模块隔离：不修改公共查询组件的默认行为。 ## 03 约束｜有哪些必须遵守的既有规则 - 沿用现有分页规则与数据权限规则，不新开口子。 - 导出走已有的异步任务通道，不新增同步大查询。 - 不引入新的第三方依赖。 ## 04 交付物｜最终交什么 - 后端查询接口 + 前端筛选组件 + 导出任务。 - 接口文档同步更新。 - 一次结构清晰、可回滚的 PR。 ## 05 验收标准｜怎样证明对 - 运行：pytest -q - 运行：python instructor/checks/task_a_acceptance.py - 筛选组合必须覆盖：单条件、多条件、空结果。 - 导出任务中的字段与列表字段一致。 - 越权访问用例必须失败；筛选不得绕过现有数据权限。 ## 执行要求 1. 先读仓库结构和 AGENTS.md，先给 5 行以内执行计划。 2. 只在允许边界内改动。 3. 完成后运行测试与独立验收脚本。 4. 最后列出：修改文件、验证证据、仍需人工确认的事项。
1
先让 Codex 给出5 行以内执行计划。
2
允许修改，完成后展示 diff。
3
跑开发测试。
pytest -q
4
跑独立验收。
python instructor/checks/task_a_acceptance.py
5
保存差异并与 Demo 1 并排。
./scripts/capture_diff.sh demo2
落点：五要素的价值不是让 Prompt 更长，而是让“完成”第一次有了共同定义。

③ 独立验收 · 28 min

新开独立验收上下文，先粘贴短指令：

# 验收｜独立责任 严格执行 validation/independent-validation.md。 重要：形成独立期望结果之前，不得读取开发实现、开发测试、开发聊天记录。
独立验收角色的完整隔离规则（需要时展开）
你是独立验收角色。你的任务不是 review 开发者的代码，而是从业务事实源重新计算“正确结果”，再与系统实际输出比较。 严格隔离： - 不读取 app/settlement/ - 不读取 tests/test_settlement_developer.py - 不读取开发角色解释、计划或聊天记录 - 只允许读取： 1. rules/settlement_source_of_truth.md 2. validation/cases.json 步骤： 1. 从 Source of Truth 独立解释规则。 2. 对每个 case 自己算出期望 mode 与 amount。 3. 先把期望写入 validation/report.md 的 Independent expectation。 4. 再运行 python -m app.settlement.cli validation/cases.json。 5. 比较期望与实际，标记 PASS / BLOCKER。 6. 出现差异后，才允许读取实现和开发侧测试。 7. 判断根因：条件遗漏、代码 bug，还是共同理解前提错误。
1
先读 Source of Truth + cases，形成独立期望。
2
再运行系统黑盒输出，对比结果。
预期 BLOCKER：GC-01 系统返回 5000 / TAX_REFUND_ONLY，独立期望为 6200 / FX_LOSS_PLUS_TAX_REFUND。
3
出现差异后，才允许读取实现与开发测试，揭示“实现和测试共享了同一错误前提”。
4
让 Code 修复；重新跑开发测试与独立验收。

Demo 4｜把这次错误变成下次不用重新教的规则

服务判断：模型的归模型，沉淀的归沉淀。

第一段｜复盘角色写入组织资产

打开此前留白的“复盘”角色，粘贴：

# 复盘｜知识沉淀责任 基于 Demo 3 的验收报告和最终修复结果，把“为什么会错、以后如何阻止”变成项目资产。 必须至少完成两项： 1. 在根目录 AGENTS.md 追加一条短而明确的候选优先级规则：组合候选先评估；只有被排除才回退到退税单候选。 2. 在 validation/checklist.md 追加一条可执行验收项，明确检查“组合候选优先级与回退条件”。 要求： - 不写故事，不写这次 case 的具体金额； - 写可复用规则； - 保持简洁； - 完成后不要继续测试“新会话是否读取”。
完成后关闭旧 Codex 会话。

第二段｜全新 Codex 会话验证沉淀

必须新会话。粘贴：

# Demo 4｜全新 Codex 会话 请读取 tasks/task-b-variant.md 并回答。 课堂观察重点：这个会话没有 Demo 3 的聊天上下文；正确候选优先级只能来自刚刚沉淀到项目级规则中的知识。
变体任务实际内容
这是一个全新会话。不要打开 rules/、validation/、app/、tests/，也不要依赖任何历史聊天。 只使用 Codex 在会话启动时自动加载的项目级规则，以及下面这组输入： - 汇损候选：符合，金额 2,400 - 退税候选：符合，金额 8,600 - 双候选排除条件：未触发 请输出： 1. 应选择的模式； 2. 金额； 3. 你依据的项目级规则原意是什么。 不要修改代码。
预期：选择 FX_LOSS_PLUS_TAX_REFUND，金额 11,000，并指出“组合候选优先，只有被排除才回退”的项目级规则。
落点：会话是新的，模型可以换，规则还在。模型的归模型，沉淀的归沉淀。
