# D0｜连续执行真机 Demo

## 任务背景

这是 `ai-rd-system-lab` 的第一个课堂 Demo，用于 AI 研发体系课程的第一讲。

课堂要证明的不是“AI 会写代码”，而是：

> Agent 已经能够在真实工程环境中读取反馈，并根据反馈自主决定下一步动作。

D0 必须足够小、足够稳、足够快。它只承担“连续执行”这一件事。

---

## 核心课堂画面

理想现场链路：

```text
Read
→ Search
→ Edit
→ Run
→ FAIL
→ Observe
→ Fix
→ PASS
```

如果经过真实预跑证明另一条链路更稳定，例如：

```text
Read → Search → Run → FAIL → Observe → Edit → Run → PASS
```

也可以接受。

**关键不是动作顺序完全一致，而是课堂必须看见：失败反馈真实进入了 Agent 的下一步决策。**

---

## 实现任务

请在本项目中实现一个独立、可重置的 `D0` workspace 和配套课堂资产。

### 1. 选择技术底座

优先调查现有：

`../ai-rd-system-demo/workspaces/demo12-financing/`

判断其中是否有适合复制的最小 Python/FastAPI baseline。

允许复制稳定的代码、测试或基础项目结构，但复制后：

- 必须放入 `ai-rd-system-lab` 自己的 workspace；
- 不允许运行时依赖旧课程目录；
- 后续两套课程可以独立修改和重置。

如果现有融资 baseline 为完成 D0 需要保留的代码过多，可以提取更小的独立 baseline，但不要为了“最小”重新造一个玩具级 hello-world 项目。

### 2. 设计一个 5–10 分钟真机任务

任务应满足：

- 有真实代码搜索和修改；
- Agent 必须运行真实命令或测试；
- 至少产生一次对下一步有意义的失败反馈；
- Agent 能从失败反馈定位并继续修复；
- 最终结果有确定性 PASS；
- 业务背景 30 秒内能讲明白；
- 代码规模足够小，观众能看懂关键变化；
- 不依赖外网服务；
- 不依赖随机数据或时间窗口；
- 不要求学员理解金融专业知识。

### 3. 不要让失败依赖“模型碰巧犯错”

这是本任务最重要的设计约束。

不能只准备一个正常需求，然后期待 Agent 第一次实现时自然写错。

请通过真实预跑选择一种可稳定复现的设计，例如：

- 现有工程约束导致最小实现触发一个已有测试；
- 一个确定的边界条件会在第一次运行时暴露；
- 一个固定的运行/类型/接口反馈能够驱动第二次修改；
- 其他不会提前泄露第三讲“独立验证”主题的确定性反馈机制。

不要使用讲师隐藏 Golden Case 来制造 D0 的第一次失败。D0 的失败必须属于**开发侧可见反馈**。

### 4. D0 不能提前讲后续课程

D0 不引入：

- 完整 Spec 方法；
- 项目记忆 / 长任务状态外置；
- Golden Case；
- 独立验收 Agent；
- Eval；
- Skill；
- 多 Agent；
- 沉淀与防复发机制。

允许存在最小 README / AGENTS 项目说明，但不要让工程环境本身成为 Demo 主角；那是 D1 的内容。

## 课堂 Runbook 必须回答

`D0-RUNBOOK.md` 至少说明：

1. 课前如何 reset；
2. 从哪个目录启动 Agent；
3. 课堂给 Agent 的完整任务文本；
4. 讲师应该观察哪几个关键节点；
5. 哪一刻应该停下来讲“Observe → Next Action”；
6. 最终用什么命令确认 PASS；
7. Agent 超时、网络异常或执行偏离时如何切到 fallback；
8. 如何恢复到 baseline 再演一次。

---

## Checkpoint 与兜底

至少准备：

### baseline

课堂正式起点。

### fallback trace

同一个 baseline、同一个任务、同一种运行方式下预跑成功的一份完整轨迹。

如果实现确实需要额外 checkpoint，可以增加，但 D0 不要做复杂的多阶段状态机。

兜底材料必须和现场使用**同一个任务、同一个 baseline**，不能拿另一个项目录像顶替。

## 验收标准

D0 只有满足以下条件才算完成：

### 工程验收

- baseline 可一键重置；
- reset 后测试/健康检查状态确定；
- 课堂任务可以真实执行；
- 最终 PASS 有机器可读结果；
- 不访问课堂外部网络服务；
- 不污染其他 Demo；
- 从全新 clone 或干净 checkout 可按 Runbook 准备成功。

### 教学验收

- 业务背景 30 秒内讲清；
- Demo 主体 5–10 分钟完成；
- 观众能看到至少一次真实反馈；
- Agent 下一步修改与该反馈存在清楚因果；
- 最终能稳定走到 PASS；
- 不提前使用独立验证 / Golden Case；
- Demo 收口只有一个：**AI 已经开始根据工程反馈连续执行。**

### 稳定性验收

在最终确定课堂任务前，用课堂计划使用的 Agent / 模型 / 权限环境重复预跑。

目标：

- 至少 10 次有效预跑；
- 记录每次耗时、关键动作、是否出现预期失败、是否最终 PASS；
- 如果“第一次失败”出现率不足以支撑稳定课堂演示，应继续调整任务设计，而不是靠讲师现场碰运气。

请保存预跑摘要，供后续验收。

---

## 实现过程建议

先调查、后实现：

1. 阅读本目录 `README.md` 和 `AGENTS.md`；
2. 调查旧融资 baseline 中 2–3 个可复用的小任务候选；
3. 先写出候选比较与推荐理由；
4. 选定后再实现 workspace、reset、verify 和 Runbook；
5. 做重复预跑；
6. 最后提交预跑结果和课堂操作摘要。

不要为了赶实现跳过候选任务验证。D0 的核心难点不是写代码，而是设计出**稳定、可解释、可重复的反馈驱动执行链**。
