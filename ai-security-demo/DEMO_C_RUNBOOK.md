# Demo C 讲师操作剧本：AI 使用合规审计与人工认定

## 课程目标

让学员区分规则筛查、模拟 AI 解释、原始证据核查和人工认定。所有案例、调用日志、制度条文、身份和证据均为虚构；服务只监听本机，不连接模型、云平台或真实集团系统。

## 正常流程

1. 打开 `http://127.0.0.1:8016/demo/c`，确认服务状态显示本地正常。
2. 选择“客服摘要 · 常规合规”，点击“开始运行”。展开日志，指出事件 ID、调用工具、脱敏元数据、准入网关和审批编号。
3. 点击“1 规则分析”。预期后端按字段计算命中，不命中规则并显示规则集、事件 ID 和制度 ID。
4. 点击“2 模拟 AI 解释”。指出解释卡标明“离线模拟 AI”，事实、推测和待核实项分开，最终结论为空。
5. 打开日志与审批原文，勾选全部证据并点击“3 核对所选证据”。再点击“导出候选问题清单 JSON”；导出项应关联事件、制度和证据，状态为待核实。
6. 选择“不违规”，填写可追溯理由，点击“4 提交人工认定”。预期审计出现固定身份 `audit-024 / ai_compliance_reviewer`、动作、结论、理由、运行和请求 ID。

## 风险线索流程

1. 选择“采购纪要 · 违规线索”，依次做规则分析和辅助解释。
2. 预期命中未准入 `browser-shell` 工具、潜在敏感输入及其脱敏元数据、绕过批准网关、外部模型、审批缺失和 30 天留存上限等线索。
3. 打开稳定 ID 为 `LIST-AI-TOOL-01` 的 AI 工具准入白名单，核对其准入项为 `customer-summary` 与 `research-search`；再对照原始调用日志、脱敏元数据和 `POL-AI-02` 制度原文。候选问题卡和导出 JSON 应链接到白名单证据 ID `EVC-C-WHITELIST-01`。完整核对后可由讲师输入理由并作“违规”人工认定；规则命中本身不是最终结论。

## 看似合理但证据不足

1. 选择“研发问答 · 证据不足”。辅助解释会提示内部模型和审批编号看似合理，同时指出资料细分类别、用途、脱敏执行和留存信息仍待核实。
2. 核对现有原始日志与 `POL-AI-03`；运行应显示关键字段缺失。导出候选问题清单，讨论应向日志所有者补问什么。
3. 完成现有证据核对后，尝试认定“违规”或“不违规”应收到 `EVIDENCE_INCOMPLETE`；选择“证据不足”，写明缺失字段和补证方向后才可提交。

## 分步、复演与重置

分步操作用于讲解每一步的依据。点击“完整复演至人工认定”会清空 C、建立当前案例、完成规则分析、辅助解释和全部原始证据核对，然后停在人工选择和确认前；自动流程不会替讲师作最终结论。点击“重置 C 演示”清空 C 的运行与审计并使旧运行 ID 失效，A/B 运行与审计不受影响。

## 故障兜底

- 页面显示本地服务不可用：查看启动终端；在 `ai-security-demo/` 执行 `make dev`，确认监听 `127.0.0.1:8016`。
- 页面显示错误：记录可见的 request ID，重置 C，再从初始状态重放。若接口返回 `INVALID_STEP`，按页面当前进度顺序点击。
- 人工认定按钮不可用：先运行规则分析、辅助解释和原文证据核对；若案例关键字段缺失，结论必须选“证据不足”；理由不得为空。
- 旧运行 ID 报错：这是重置后的预期保护，重新开始案例即可。
- 无法下载问题清单：先完成规则分析后重试；也可打开 `/api/v1/c/runs/{run_id}/candidate-questions` 保存返回 JSON。该列表是本地候选问题，不代表调查结论。
